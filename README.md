# Регион — управление региональным сбытом

Веб-приложение по курсовой работе «Программное средство управления региональной сбытовой политикой предприятия на основе анализа покупательной способности населения».

Работают регистрация и вход, управление пользователями и региональными назначениями, каталог, история цен, журнал отгрузок и согласование региональных планов продаж с аналитическим расчётом и отчётом план/факт. Для каталога, прайсов и отгрузок доступны файлы Excel.

## Состав

| Компонент | Технологии |
| --- | --- |
| `backend/` | Java 21, Spring Boot 3.5, Maven, Spring Security, JPA, Flyway, OpenAPI |
| `frontend/` | React 19, TypeScript, Vite, npm |
| Постоянные данные | MySQL 8.4, отдельный Docker volume |
| Инфраструктура будущей аналитики | Redis 7.4; прикладное кэширование будет добавлено вместе с аналитикой |

Backend и frontend — самостоятельные проекты. `backend/pom.xml` можно открыть в IntelliJ IDEA; `frontend/` — в IntelliJ IDEA или VS Code.

## Требования

Установите JDK 21, Node.js 22.12+ или 24 LTS, Docker с Docker Compose v2. Maven 3.9.11 запускается через включённый Maven Wrapper; установленный Maven 3.9+ также подходит. На Windows Docker Desktop должен работать в режиме Linux containers. Порты 3306, 6379, 8080 и 5173 должны быть свободны.

В `.env` необходимо заполнить `MYSQL_PASSWORD` и `MYSQL_ROOT_PASSWORD` разными паролями; если храните там `DB_PASSWORD`, укажите тот же пароль, что у `MYSQL_PASSWORD`.

Для базового запуска Google credentials не нужны: вход по логину и паролю работает независимо, а Google-кнопка объясняет, что провайдер не настроен.

## Первый запуск

Выполняйте команды из корня репозитория. Создайте локальный `.env` из `.env.example` и замените пароли MySQL. Не добавляйте `.env` в Git.

PowerShell:

```powershell
Copy-Item .env.example .env
notepad .env
docker compose up -d mysql redis
docker compose ps
```

Linux/macOS:

```bash
cp .env.example .env
# Отредактируйте .env перед первым запуском.
docker compose up -d mysql redis
docker compose ps
```

Дождитесь состояния `healthy` у MySQL. `.env` автоматически читает Docker Compose, но Spring Boot сам по себе этот файл не загружает. Передайте настройки backend через переменные окружения в том терминале, в котором запускаете Java.

PowerShell, отдельное окно backend:

```powershell
$env:DB_URL = 'jdbc:mysql://localhost:3306/regional_sales?connectionTimeZone=UTC'
$env:DB_USERNAME = 'regional_sales'
# Введите тот же пароль, который указан в MYSQL_PASSWORD вашего .env.
$dbPassword = Read-Host 'Пароль пользователя MySQL' -AsSecureString
$env:DB_PASSWORD = [System.Net.NetworkCredential]::new('', $dbPassword).Password
cd backend
./mvnw.cmd spring-boot:run
```

Bash, отдельный терминал backend:

```bash
export DB_URL='jdbc:mysql://localhost:3306/regional_sales?connectionTimeZone=UTC'
export DB_USERNAME='regional_sales'
read -rsp 'Пароль пользователя MySQL: ' DB_PASSWORD; echo
export DB_PASSWORD
cd backend
./mvnw spring-boot:run
```

Если вы изменили `MYSQL_DATABASE` или `MYSQL_USER`, измените URL и имя пользователя соответственно. В стандартном запуске Hibernate проверяет схему, а Flyway последовательно применяет версионированные SQL-миграции. Схема и данные не пересоздаются при каждом старте.

В новом терминале frontend:

```bash
cd frontend
npm ci
npm run dev -- --host 0.0.0.0
```

Откройте `http://localhost:5173`. Backend работает на `http://localhost:8080`; Swagger — `http://localhost:8080/swagger-ui/index.html`. Vite проксирует API и OAuth-адреса на backend. Для CSRF и cookie-сессии открывайте интерфейс через один и тот же hostname, например `localhost`.

### Учётные записи и роли

Предустановленных пользователей и общих тестовых паролей нет. Зарегистрируйте учётную запись через форму. Она получает роль `MANAGER` (менеджер), без назначенных регионов. При регистрации нельзя выбрать роль администратора или руководителя.

Для первого администратора перед запуском backend задайте `BOOTSTRAP_ADMIN_LOGIN`, `BOOTSTRAP_ADMIN_EMAIL`, `BOOTSTRAP_ADMIN_PASSWORD` и, при необходимости, `BOOTSTRAP_ADMIN_FULL_NAME`. Используйте отдельный пароль длиной не менее 12 символов. Пример безопасного ввода пароля в PowerShell:

```powershell
$env:BOOTSTRAP_ADMIN_LOGIN = 'admin'
$env:BOOTSTRAP_ADMIN_EMAIL = 'admin@example.org'
$env:BOOTSTRAP_ADMIN_FULL_NAME = 'Администратор системы'
$adminPassword = Read-Host 'Новый пароль администратора' -AsSecureString
$env:BOOTSTRAP_ADMIN_PASSWORD = [System.Net.NetworkCredential]::new('', $adminPassword).Password
# В этом же терминале, из backend/:
./mvnw.cmd spring-boot:run
```

В Bash используйте `export` для тех же имён и `read -rsp` для пароля. Backend применяет эти параметры один раз при отсутствии учётных записей с ролью администратора. После создания администратора удалите bootstrap-переменные из постоянной конфигурации.

| Код | Название | Предметная зона для следующих этапов |
| --- | --- | --- |
| `ADMIN` | Администратор | Пользователи, роли и региональные назначения |
| `MANAGER` | Менеджер по продажам | Каталог, отгрузки закреплённых регионов и подготовка планов |
| `ANALYST` | Региональный аналитик | Статистика, индексы и рекомендации |
| `SALES_HEAD` | Руководитель отдела сбыта | Региональные планы и согласование |

Список доступных разделов зависит от роли. Разделы без реализованных операций не выдают демонстрационные показатели за реальные данные.

Войдите администратором и откройте раздел **Пользователи**. Нажмите **Создать пользователя**, задайте логин, ФИО, email, начальный пароль и роль. В списке доступны поиск и фильтры по роли и статусу. Действие **Изменить** открывает данные, роль и смену пароля, а **Регионы** позволяет задать, изменить или отменить период доступа менеджера.

Для завершения доступа используйте **Заблокировать**. После блокировки или смены пароля прежние сеансы завершаются при следующем запросе. Активация позволяет снова войти в систему. Flyway добавит поле версии сессии в существующую базу при запуске backend.

### Каталог товаров

Войдите как менеджер по продажам с действующим назначением региона. В разделе **Продукция** можно добавлять и редактировать карточки, снимать позиции с продажи и возвращать их. Для пакетной загрузки выберите **Импорт каталога** и откройте `01_nomenklatura.xlsx` из комплекта «Светоприбор». Существующие позиции обновляются по артикулу, а ошибки файла отображаются с номерами строк. **Скачать каталог** выдаёт Excel в том же формате. [Формат каталога и импорта](docs/API.md#каталог-продукции)

В **Истории цен** менеджер может сохранить отпускные цены активных товаров за выбранный год и квартал. Сначала обновите каталог из номенклатуры, затем выберите **Сохранить цены из каталога**. Операция добавляет записи за квартал для товаров без цены за этот период.

Для квартальных файлов выберите **Импорт прайсов** в **Истории цен** и укажите один или несколько Excel из папки `02_praisy`. Артикулы прайсов должны быть в каталоге. Подтвердите замену, если система нашла цены с теми же артикулами и датами. Историю можно искать по товару, артикулу и коду прайса, фильтровать по товару и периоду и листать по 10, 25 или 50 записей. [Формат прайса и API истории цен](docs/API.md#история-цен)

### Журнал отгрузок

В разделе **Отгрузки** менеджер регистрирует поставки в закреплённые регионы. Для пакетного ввода загрузите `shipments_2024-Q1.xlsx` или другой квартальный файл через **Импорт из Excel**. Предварительно загрузите номенклатуру. Результат покажет добавленные строки, совпадения с журналом и количество строк вне действующих назначений.

Поиск работает по ключу строки документа, товару, артикулу и региону. Доступны фильтры по датам, региону и товару, сортировка по столбцам и размеры страницы 10, 25 и 50. Аналитик и руководитель отдела сбыта могут просматривать общий журнал. [Формат импорта и API отгрузок](docs/API.md#отгрузки)

### Региональные планы

1. Администратор закрепляет менеджера за регионом. Руководитель открывает **Региональные планы → Новый план**, задаёт регион, ответственного, период, целевую выручку и ограничения и нажимает **Передать на анализ**.
2. Программа проверяет журнал отгрузок за предыдущий сопоставимый период. При наличии данных она фиксирует число строк и выручку и создаёт задание аналитику. Если журнал пуст за этот период и регион, менеджер дополняет его. После регистрации или импорта подходящих отгрузок задание автоматически появляется у аналитика.
3. Аналитик открывает задание в разделе **Покупательная способность** или на главной панели, проверяет показатели, рассчитывает индекс и пишет рекомендацию. Кнопка **Сохранить и передать менеджеру** открывает ответственному менеджеру редактирование проекта.
4. Менеджер выбирает товары, плановые количества и цены и нажимает **Проверить проект плана**. Программа проверяет позиции, достижение цели по выручке и предельную скидку. После проверки позиций проект появляется у руководителя в разделе **Согласование планов**. Для расчёта затрат и проверки ресурсов потребуются данные о себестоимости и остатках.
5. Руководитель утверждает проект, возвращает его с замечаниями или оформляет отказ. Замечания к позициям получает менеджер. Уточнение расчёта и рекомендации можно поручить аналитику. Утверждённый план появляется на главной панели менеджера. В **Отчётности** его показатели сопоставляются с отгрузками за плановый период.

Основной маршрут проходит через **Черновик → На анализе → В работе → На согласовании → Утверждён**. При отсутствии отгрузок план переходит в **Исправление данных о продажах**, при ошибках в позициях — в **Требует исправления**. Менеджер может отозвать проект на редактирование до принятия решения.

Руководитель видит все статусы. В колонке **Действия** можно отменить активный неутверждённый план или удалить неутверждённый план после подтверждения. Отменённая запись остаётся в списке, а её регион и период освобождаются для нового плана. При запуске программа перепроверяет ранее переданные планы на этапе подготовки сведений. Подходящие отгрузки переводят такие планы на анализ с сохранёнными позициями.

В блоке **Статистика → Зарплаты Белстата по регионам** кнопка **Скачать с Белстата** открывает архив на сервере приложения, находит выпуски за выбранный или последний опубликованный год и считывает начисленную зарплату в BYN по шести областям и г. Минску из Excel. Успешные выпуски сохраняются по месяцам с источником, повторная загрузка обновляет тот же период. Для скачивания машине с бэкендом нужен доступ к belstat.gov.by.

В разделе **Статистика → Импорт данных Белстата** аналитик загружает три книги XLSX со средней номинальной зарплатой за год в BYN в месяц, годовым розничным товарооборотом и населением. В таблицах нужны названия шести областей и г. Минска по строкам или столбцам и годовые значения по другой оси. Аналитик выбирает единицы оборота и населения, как в выгрузке. Программа берёт последний общий завершённый год с полным набором регионов и пересчитывает оборот на одного жителя. Повторная загрузка обновляет значения за тот же год.

Для нового расчёта плана используется последний загруженный полный год, завершившийся до начала планового периода. Если подходящей выгрузки ещё нет, расчёт помечается как учебный. Сохранённые рекомендации содержат снимок использованных показателей. Индекс нормализует зарплату, оборот на жителя и население по минимуму и максимуму. Одинаковые значения дают 0,5. Веса по умолчанию равны 40 %, 40 % и 20 %.

Ценовой ориентир рассчитывается как разница индекса региона и среднего индекса, умноженная на 10 процентных пунктов. Коэффициент ограничен диапазоном от −5 % до +5 %, а снижение дополнительно ограничено допустимой скидкой плана. Менеджер применяет предложенную цену к позиции вручную. Базой служит прайс на начало периода или цена каталога. В **Аналитике** доступны сохранённые сравнения, а в **Рекомендациях** — выводы и ссылки на планы.

## Google-вход

1. Создайте OAuth client типа **Web application** в Google Cloud Console и настройте consent screen. В режиме Testing добавьте свои Google-аккаунты в Test users.
2. Укажите Authorized JavaScript origin `http://localhost:5173` и Authorized redirect URI `http://localhost:8080/login/oauth2/code/google`.
3. В окружении backend задайте `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET`; для локального интерфейса оставьте `FRONTEND_URL=http://localhost:5173`.
4. Перезапустите backend. `GET /api/auth/providers` должен вернуть `{"google":true}`.
5. Нажмите кнопку Google. После успешного входа приложение откроет защищённую главную страницу.

Client secret вводится только в локальные переменные окружения или секреты среды. Он не попадает в frontend, Git и URL. Проверяются OpenID Connect, подтверждение email и постоянный идентификатор `sub`. Совпадение email с локальной учётной записью само по себе не связывает аккаунты. Новый Google-пользователь получает роль `MANAGER` без назначений регионов. Для production зарегистрируйте HTTPS callback, настройте `FRONTEND_URL`, `GOOGLE_REDIRECT_URI` и задайте `COOKIE_SECURE=true`.

Полный реальный вход через Google требует ваших OAuth credentials и согласия пользователя в браузере; локальные тесты провайдера не заменяют такую проверку.

## Проверки

Backend (Linux/macOS):

```bash
cd backend
./mvnw test
./mvnw package
```

На Windows в PowerShell используйте `./mvnw.cmd test` и `./mvnw.cmd package`. Можно заменить wrapper-команды на `mvn`, если Maven установлен.

Frontend:

```bash
cd frontend
npm test
npm run build
```

В обычном `mvn test` MySQL-интеграционные тесты пропускаются. Для их выполнения используйте отдельную тестовую БД MySQL, задайте обычные `DB_*` для неё и `MYSQL_INTEGRATION_TESTS=true`, затем запустите `./mvnw -Dtest=MySqlSchemaIntegrationTest test`. Не запускайте такие проверки на production-базе.

Тесты авторизации на H2 проверяют прикладную логику и HTTP-контракты; они не доказывают совместимость SQL-миграций с MySQL. Запуск с обычным профилем и реальной MySQL нужен для проверки Flyway, внешних ключей и вычисляемых столбцов. Результаты выполненных проверок фиксируются отдельно от списка команд.

Для ручной проверки: зарегистрируйтесь, обновите страницу, выйдите, убедитесь в недоступности профиля после выхода; проверьте неправильный пароль и недопустимую форму регистрации. В Swagger методы изменения данных также требуют cookie-сессию и CSRF-заголовок.

## Сохранение данных и остановка

```bash
docker compose stop
# Повторный запуск с сохранёнными данными:
docker compose up -d mysql redis
```

`docker compose down` удаляет контейнеры, сохраняя именованные volumes. Команда с `-v` удаляет данные и для обычной остановки не нужна. После первой инициализации MySQL изменение пароля в `.env` само по себе не меняет пользователя в существующем volume: меняйте пароль средствами MySQL и синхронизируйте конфигурацию backend.

Остановка frontend/backend: `Ctrl+C` в соответствующих терминалах. Сессии хранятся в памяти backend и завершаются при его перезапуске; пользователи и предметные данные остаются в MySQL.
