# Принятые технические решения

## Границы текущего этапа

Последнее прямое указание пользователя ограничивает реализацию регистрацией/входом, включая Google, базой данных, классами предметной области и заглушками страниц. Общий документ PROJECT_CONTEXT_FOR_CODEX описывает целевой продукт целиком. Его импорт статистики, аналитические алгоритмы, планирование, кэширование и отчёты сохранены в плане, но не объявлены выполненными на этом этапе.

Изучены техническое задание PROJECT_CONTEXT_FOR_CODEX, пояснительная записка «КП ИИСИК Татарчук» и бланк задания с методическими пометками. Бланк устанавливает требования к конечной курсовой работе: минимум 10 взаимосвязанных таблиц, ролевой доступ, межкомпонентная интеграция, минимум три предметных алгоритма и проверяемый сквозной сценарий. Текущий этап создаёт основу, а не заменяет выполнение всех этих требований.

## Разрешение противоречий источников

| В источниках | Решение |
| --- | --- |
| Во введении и заключении записки остались PostgreSQL, контент-маркетинг, GitHub-вход и другие роли | Используется предметная модель регионального сбыта, MySQL и Google согласно прямому запросу пользователя и техническому заданию |
| На ER-изображении видны не все связи, а таблица атрибутов и контекст содержат больше | Включены связи плана и рекомендации с расчётом покупательной способности, а рекомендации — с регионом |
| Записка предусматривает создание пользователя администратором | Пользователь дополнительно запросил самостоятельную регистрацию; она выдаёт только роль менеджера без коммерческого регионального доступа |
| В части описания ролей менеджер лишь просматривает продукцию, UC-02 предусматривает ведение каталога | Для последующих этапов принята матрица UC из записки: менеджер ведёт каталог; сейчас доступен только просмотр |
| Общий документ требует действующих форм всех модулей, последний запрос — заглушки страниц | Для текущего этапа работают формы идентификации; остальные модули честно помечены как следующие этапы |

## Архитектура и данные

Применён модульный монолит: отдельное React SPA обращается к Spring Boot через REST; данные сохраняются в MySQL. Это сохраняет единую транзакционную модель без инфраструктурных издержек микросервисов. React не входит в Maven-модуль.

Схема управляется Flyway, JPA использует проверку существующей схемы. Имена таблиц приведены к `snake_case`; `User` называется `app_users`, чтобы не использовать неоднозначное системное имя. Идентификаторы внутри Java — `Long`, внешние ключи ссылаются на конкретную сущность, а не хранят свободные текстовые значения.

Реализованы 13 основных сущностей модели. Добавлена `OAuthIdentity`: постоянная связь пользователя с провайдером и `sub`. В `AppUser` добавлен email, а хеш пароля допускает отсутствие для Google-only аккаунта. Не создаются случайные пароли, которые затем невозможно сообщить владельцу. Наличие Google identity не предоставляет привилегий сверх обычной роли.

Деньги и количества представлены `BigDecimal`; денежные столбцы — `DECIMAL`, даты периодов — `DATE`. Исторические цены сохраняются в отгрузках и плановых позициях. Суммы отгрузок и позиций плана вычисляются MySQL в `STORED`-столбцах; JPA не записывает их вручную. Уникальные ограничения предотвращают дубли статистики и позиций плана. Внешние ключи с `ON DELETE RESTRICT` защищают связанную историю. Для `approved_by_user_id` используется `ON UPDATE RESTRICT`: MySQL запрещает сочетание `ON UPDATE CASCADE` и CHECK по тому же столбцу. Проверка согласованности статуса и реквизитов утверждения сохранена.

Для плана добавлена версия оптимистической блокировки. Это подготовка к конкурентному редактированию; она сама по себе не реализует процесс согласования и запрет изменения утверждённого плана. Будущий сервис должен проверять статус и права в транзакции.

## Аутентификация и безопасность

Используется серверная HTTP-сессия с HttpOnly cookie, BCrypt и Spring Security. JWT и хранение токенов в `localStorage` для этого сценария не требуются. Вход и регистрация создают сессию; выход инвалидирует её. CSRF применяется к изменяющим состояние запросам, включая регистрацию, вход и выход. Frontend получает токен отдельным GET и обновляет его после смены состояния аутентификации. При коде `CSRF_INVALID` клиент обновляет токен и повторяет запрос ровно один раз; обычные ошибки прав и сетевые сбои не повторяются.

Проверка роли выполняется на backend. Ответы REST используют 401 для отсутствующей аутентификации и 403 для недостаточных полномочий. Скрытие разделов интерфейса дополняет, но не заменяет серверную защиту. Для менеджера справочник доступных регионов ограничен текущими назначениями с учётом начальной и конечной даты. Без назначения список пуст.

Google интегрирован через OpenID Connect в Spring Security, а не через доверие email из frontend. Проверяются подтверждённость email и неизменяемый идентификатор Google `sub`. Локальный пользователь не связывается автоматически с Google только по совпавшему email: иначе провайдер мог бы неявно заменить предусмотренный способ входа. Отдельный интерфейс связывания аккаунтов пока отсутствует.

Если Google credentials не настроены, провайдер выключен, а парольная авторизация продолжает работать. Адрес возврата задаётся серверной настройкой `FRONTEND_URL`, а не произвольным пользовательским параметром.

Первый администратор создаётся из явно переданных bootstrap-переменных. Общих парольных учётных записей в миграциях нет. Этот механизм предназначен для начальной настройки, а не для сброса паролей существующих пользователей.

Предметные коммерческие данные и аналитические показатели не выдумываются для заполнения экранов. Начальные справочники не являются статистикой Белстата.

## Проверка и эксплуатационные пределы

H2 в тестовом профиле нужен для быстрых HTTP- и сервисных тестов. Он не заменяет MySQL 8.4 при проверке Flyway, generated columns, индексов и типов. Реальный Google redirect flow требует OAuth credentials, доступа к Google и интерактивного входа пользователя.

Для локального запуска разрешён HTTP. При публикации нужны HTTPS, защищённые cookie и корректные доверенные настройки reverse proxy. Сессии сейчас локальны процессу backend: после рестарта требуется новый вход. MySQL остаётся источником постоянных данных. Распределённые сессии, восстановление пароля, подтверждение email для локальной регистрации, MFA и интерфейс связывания провайдеров в текущий этап не включены.
