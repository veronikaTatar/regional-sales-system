# REST API текущего этапа

Базовый путь backend: `/api`. Примеры используют локальный адрес `http://localhost:8080`. Frontend обращается по относительным адресам через Vite proxy.

## Сессия и CSRF

1. Вызвать `GET /api/auth/csrf`, сохраняя cookie сервера.
2. Получить `{ "token": "…", "headerName": "X-CSRF-TOKEN" }`.
3. Для каждого POST, PATCH, PUT и DELETE передать токен в указанный заголовок и cookie (`credentials: 'include'` в fetch). Для тела JSON указать `Content-Type: application/json`.
4. После входа, регистрации и выхода запросить новый CSRF-токен.

Cookie `REGSALES_SESSION` имеет `HttpOnly` и `SameSite=Lax`; её значение не читается JavaScript. Период неактивности сессии — 30 минут. REST-запрос без действующей аутентификации возвращает JSON с 401, а не HTML-форму входа. Разрешение на страницу в frontend не заменяет API-проверку.

### Регистрация

```json
{
  "login": "manager01",
  "email": "manager@example.org",
  "fullName": "Анна Иванова",
  "password": "your-own-strong-password"
}
```

Успешная регистрация возвращает 201, вход и профиль — 200. Логин содержит 3–60 латинских букв, цифр, точек, дефисов или подчёркиваний; пароль — 8–72 символа и не более 72 байт UTF-8. Логин и email нормализуются к нижнему регистру.

Роль и назначения не принимаются из публичной формы. Нельзя передать `role: "ADMIN"`, чтобы получить повышенные права. Все ограничения длины и формата проверяет backend; frontend показывает соответствующие ошибки.

### Вход

```json
{
  "login": "manager01",
  "password": "your-own-strong-password"
}
```

Вход по логину — отдельное поле, он не подменяется email. Регистрация, вход и `/me` возвращают профиль без хеша пароля:

```json
{
  "id": 12,
  "login": "manager01",
  "email": "manager@example.org",
  "fullName": "Анна Иванова",
  "role": "MANAGER",
  "roleName": "Менеджер по продажам",
  "active": true
}
```

### Управление пользователями

`POST /api/users` принимает `login`, `email`, `fullName`, `password` и обязательную `role` из `GET /api/roles`. Ответ 201 содержит активный профиль созданного пользователя. Администратор продолжает работать в своей сессии. `GET /api/users` добавляет к профилю `hasRegionAssignments` для просмотра сохранённых назначений.

Пример изменения через `PATCH /api/users/12`.

```json
{
  "fullName": "Анна Петрова",
  "email": "anna.petrova@example.org",
  "role": "ANALYST",
  "active": true
}
```

Поля `login`, `email`, `fullName`, `password`, `role` и `active` можно изменять по отдельности или вместе. Пустое изменение возвращает 400, повторяющийся логин или email — 409 с ошибками соответствующих полей. Администратор может изменить собственные данные и пароль. Попытка заблокировать себя или снять свою роль возвращает 409.

Смена роли и данных профиля учитывается при следующем запросе. Блокировка (`"active": false`) или новый пароль отзывают прежние сессии. Активация (`"active": true`) позволяет войти заново. Запись пользователя и связанные с ней данные сохраняются.

### Назначения регионов

`POST` и `PUT` принимают идентификатор региона и даты в формате ISO. Для бессрочного назначения поле `endDate` можно опустить или передать `null`.

```json
{
  "regionId": 1,
  "startDate": "2026-11-20",
  "endDate": "2026-12-31"
}
```

Даты включительны и сверяются с календарём Беларуси при выдаче доступа. Пересечение периодов для одного менеджера и региона возвращает 409. Создавать и изменять назначения можно для роли `MANAGER`. При смене роли или блокировке строки назначений сохраняются. Администратор может просмотреть или отменить их перед восстановлением доступа. Успешный `DELETE` возвращает 204.

### Каталог продукции

Каталог общий для предприятия. Менеджер с действующим назначением региона может вести каталог и скачивать Excel. `GET /api/products/manage` возвращает `canManage` и массив `products`. При `canManage: true` список включает снятые с продажи позиции. При `canManage: false` он содержит активные товары.

При создании и редактировании используются `sku`, `name`, `unit` и `currentPrice`. Цена передаётся в BYN без НДС с точностью до двух знаков. Поля `category`, `description` и `priceAsOf` необязательны. Дата цены записывается в формате `ГГГГ-ММ-ДД`. Созданный товар активен. Для изменения статуса передайте `{"active": false}` или `{"active": true}` в `PATCH /api/products/{id}/status`.

`POST /api/products/import` принимает `multipart/form-data` с полем `file`. Подходит книга `01_nomenklatura.xlsx`. Формат XLSX, до 1 МБ и 5 000 товарных строк. Заголовки находятся в первой строке листа «Товары» или первого листа книги. Обязательны «Артикул», «Наименование», «Ед. изм.» и «Отпускная цена без НДС, BYN». Поддерживаются «Товарная группа», «Характеристики», «Цена на дату» и «Активен». Формулы в этих колонках следует заменить значениями.

Импорт добавляет новые позиции и обновляет существующие по артикулу. При пропуске столбца товарной группы или характеристик сохраняется значение из каталога. Пропущенный статус сохраняется для существующих товаров, а новый товар становится активным. Если цена изменилась и дата цены отсутствует, дата очищается.

Успешный ответ содержит счётчики `total`, `created`, `updated` и `unchanged`. Некорректные строки возвращают 422 с их номерами в `fieldErrors`. Вся загрузка выполняется одной транзакцией. Файл, скачанный через `GET /api/products/export`, использует те же заголовки.

### История цен

История общая для предприятия. Все операции доступны менеджеру с действующим назначением региона.

- `GET /api/products/price-history` возвращает цены с артикулом, названием и включительными датами действия. Отпускная цена без НДС возвращается в поле `unitPrice`. При наличии в прайсе возвращаются также `vatRate`, `priceWithVat`, `retailPrice` и `priceListCode`.
- `POST /api/products/price-history/snapshot` принимает `{"year": 2026, "quarter": 4}` и добавляет отпускные цены активных товаров за указанный календарный квартал. Для товара с готовой записью за те же даты результат учитывается в `unchanged`.
- `POST /api/products/price-history/import` принимает `multipart/form-data` с повторяющимся полем `files` или одним полем `file`. Подходит лист «Прайс» из `price_list_2024-Q1.xlsx`. Обязательны заголовки «Артикул», «Действует с», «Действует по» и «Отпускная без НДС, BYN». Можно указать код прайс-листа, валюту BYN, ставку НДС, отпускную цену с НДС и розничный ориентир с НДС. За раз принимается до 24 файлов XLSX по 1 МБ и до 5 000 строк в сумме.

Строки связываются с каталогом по артикулу. Совпадение сохранённой цены по товару и датам возвращает `409 PRICE_PERIOD_EXISTS` с `replacementToken` и примерами совпадений в `fieldErrors`. Для подтверждения отправьте тот же пакет с полем `replacementToken`. При изменении записей до подтверждения сервер выдаёт новый запрос подтверждения. Пересекающиеся периоды, повторные строки в пакете и неизвестные артикулы возвращают ошибки без записи в историю. Импорт и сохранение квартала возвращают счётчики `total`, `created`, `updated` и `unchanged`.

### Отгрузки

Менеджер работает с регионами действующих назначений. Региональный аналитик и руководитель отдела сбыта просматривают общий журнал.

- `GET /api/shipments` возвращает `shipments`, `total`, `page` и `pageSize`. Фильтры `regionId`, `productId`, `from` и `to` применяются совместно с `search`. Обе даты включительны. Нумерация `page` начинается с 0, `size` принимает значения от 1 до 50. `sort` принимает `DATE`, `REFERENCE`, `REGION`, `PRODUCT`, `QUANTITY`, `PRICE` или `TOTAL`, `direction` принимает `ASC` или `DESC`. По умолчанию сначала показаны новые отгрузки. Сумма `totalAmount` передаётся десятичной строкой с точностью до копейки.
- `GET /api/shipments/options` возвращает `canRecord`, регионы и товары для фильтров и регистрации.
- `POST /api/shipments` регистрирует отгрузку по `regionId`, `productId`, `shipmentDate`, `quantity`, `unitPrice` и необязательному `referenceNumber`. Количество указывается с точностью до трёх знаков. `unitPrice` содержит фактическую цену единицы без НДС с учётом скидки. Сумма рассчитывается в БД.
- `POST /api/shipments/import` принимает XLSX до 1 МБ и 5 000 строк в поле `file`. Обязательны заголовки «Ключ строки», «Дата отгрузки», «Код региона ISO», «Артикул», «Количество» и «Цена ед. без НДС, BYN». При наличии столбца «Сумма без НДС, BYN» его значения сверяются с произведением количества и цены с округлением до копейки. Ключ строки должен быть уникальным. Повторные совпадения учитываются в `unchanged`, строки вне назначений в `skipped`, новые в `created`. При ошибке весь файл отклоняется с номерами строк в `fieldErrors`.

### Региональные планы

- `GET /api/plans` возвращает все сохранённые статусы для руководителя, очередь `AWAITING_ANALYSIS` для аналитика и задания для аутентифицированного менеджера в регионах его действующих назначений. `attention=true` показывает активные задачи этих ролей и утверждённые планы менеджера.
- `GET /api/plans/options` даёт руководителю активные регионы и закреплённых за ними менеджеров. `GET /api/plans/{id}` возвращает параметры, позиции, доступные действия, сводку представленных продаж и фактическую выручку по сопоставимым периодам.
- Руководитель использует `POST /api/plans` и `PUT /api/plans/{id}` для периода `periodStart`–`periodEnd`, региона `regionId`, менеджера `managerId` и целевой выручки `targetRevenue`. `budgetLimit`, `maxDiscountPercent` и `planningComment` необязательны. При `requestAnalysis: true` программа проверяет журнал и переводит план в `AWAITING_ANALYSIS`, если за предыдущий сопоставимый период есть отгрузки по этому региону. Иначе план получает `SALES_REVISION`, а менеджер дополняет журнал.
- `POST /api/plans/{id}/sales?version=…` повторно проверяет отгрузки за предыдущий сопоставимый период и доступен ответственному менеджеру на этапе подготовки сведений. При наличии отгрузок для региона фиксируются число строк, выручка и дата передачи в `salesSubmission`. План переходит в `AWAITING_ANALYSIS`. При отсутствии данных возвращается `SALES_REVISION` с `validationNote`.
- `POST /api/plans/{id}/analysis/preview` принимает `version` и `weights` с долями `salary`, `retail` и `population` в процентах. Аналитик получает индекс, ранжирование и ценовой ориентир. `PUT /api/plans/{id}/analysis` дополнительно принимает `recommendationText`. Снимок показателей и вывод сохраняются, а менеджер получает проект в статусе `IN_PROGRESS`. `GET /api/plans/{id}` возвращает `recommendation`, а `offers` могут содержать `suggestedUnitPrice`.
- Ответственный менеджер использует `PUT /api/plans/{id}/items` и передаёт полный список `items` с `productId`, `plannedQuantity`, `plannedUnitPrice`. При `submit: true` ошибки в позициях приводят к `NEEDS_CORRECTION` и `validationNote` с сохранением прежних позиций. Если позиции корректны, план переходит в `IN_REVIEW`, а `planningCheck` содержит результаты сравнения с целью по выручке и предельной скидкой. Сохранение без отправки оставляет проект в `IN_PROGRESS`. Сумма строки округляется до копейки. Денежные значения в ответах передаются десятичными строками в BYN без НДС.
- Руководитель использует `POST /api/plans/{id}/review` с решением `APPROVE`, `RETURN`, `RETURN_ANALYSIS` или `REJECT`. Утверждение фиксирует пользователя и время. При `RETURN` менеджер исправляет позиции из статуса `REVISION`. При `RETURN_ANALYSIS` план возвращается в `AWAITING_ANALYSIS` для уточнения рекомендации. Отказ завершает планирование статусом `REJECTED`. Для замечаний и отказа обязателен `reviewComment`. Для изменений существующего плана требуется актуальная `version`. `409 PLAN_CHANGED` означает, что карточку следует обновить, а `409 PLAN_STAGE` означает, что действие недоступно при текущем статусе.
- `POST /api/plans/{id}/withdraw?version=…` позволяет ответственному менеджеру вернуть проект из `IN_REVIEW` в `IN_PROGRESS` для редактирования. Позиции и аналитическая рекомендация сохраняются.
- `POST /api/plans/{id}/cancel?version=…` переводит активный неутверждённый план в `CANCELLED`. `DELETE /api/plans/{id}?version=…` удаляет неутверждённый план и его позиции с ответом `204`. Оба действия доступны руководителю. Отменённые планы допускают создание нового плана на тот же регион и период.
- `GET /api/plans/results` возвращает утверждённые планы и фактическую выручку за периоды планов. Для менеджера применяются те же назначения, что и в списке планов.

### Аналитика

- `GET /api/analytics/statistics?periodStart=2026-01-01&periodEnd=2026-03-31` доступен аналитику. Пока источник помечен `TRAINING`, значения подставляются из учебного набора. Период задаётся календарным месяцем или кварталом.
- `GET /api/analytics/recommendations` возвращает опубликованные рекомендации для аналитика и руководителя. `GET /api/analytics/recommendations/{planId}` возвращает сохранённые показатели, веса, ранжирование, версию метода и рекомендацию по выбранному плану.

## Google OpenID Connect

Начало потока: `GET /oauth2/authorization/google` в браузере, callback: `/login/oauth2/code/google`. Это OAuth redirect flow, а не JSON-endpoint для передачи email или frontend-токена. После успешного входа backend направляет браузер на настроенный `FRONTEND_URL`; при ошибке — на страницу входа с признаком ошибки.

Если Google не настроен, `/api/auth/providers` сообщает `false`; парольный вход продолжает работать. Для создания Google-only аккаунта нужен подтверждённый email. Существующая локальная запись с таким же email не связывается автоматически.

## Ошибки

Общий формат:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Проверьте введённые данные",
  "fieldErrors": {
    "email": "Укажите корректный email"
  }
}
```

| HTTP | Значение |
| --- | --- |
| 400 | Неверный формат или обязательные поля |
| 401 | Неверные учётные данные или отсутствует действующая сессия |
| 403 | Недостаточно прав (`FORBIDDEN`) либо отсутствует/неверен CSRF-токен (`CSRF_INVALID`) |
| 404 | Запрашиваемый ресурс не существует |
| 409 | Уникальность или конфликт состояния |

Точные коды ошибок зависят от операции; клиент должен ориентироваться на HTTP-статус и поле `code`, а пользователю показывать `message`.

## Планируемые API

На следующих этапах предусмотрены импорт статистики, подключение официальных источников и Excel-экспорт отчётов.
