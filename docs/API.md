# REST API текущего этапа

Базовый путь backend: `/api`. Примеры используют локальный адрес `http://localhost:8080`. Frontend обращается по относительным адресам через Vite proxy.

## Сессия и CSRF

1. Вызвать `GET /api/auth/csrf`, сохраняя cookie сервера.
2. Получить `{ "token": "…", "headerName": "X-CSRF-TOKEN" }`.
3. Для каждого POST/PATCH передать токен в указанный заголовок, `Content-Type: application/json` и cookie (`credentials: 'include'` в fetch).
4. После входа, регистрации и выхода запросить новый CSRF-токен.

Cookie `REGSALES_SESSION` имеет `HttpOnly` и `SameSite=Lax`; её значение не читается JavaScript. Период неактивности сессии — 30 минут. REST-запрос без действующей аутентификации возвращает JSON с 401, а не HTML-форму входа. Разрешение на страницу в frontend не заменяет API-проверку.

## Действующие операции

| Метод | Путь | Доступ | Назначение |
| --- | --- | --- | --- |
| GET | `/api/auth/csrf` | Публичный | Получить CSRF-токен |
| GET | `/api/auth/providers` | Публичный | Возможность входа Google, `{ "google": boolean }` |
| POST | `/api/auth/register` | Публичный + CSRF | Создать менеджера и начать сессию |
| POST | `/api/auth/login` | Публичный + CSRF | Вход по логину и паролю |
| GET | `/api/auth/me` | Вошедший пользователь | Текущий профиль |
| POST | `/api/auth/logout` | CSRF | Завершить сессию; 204 |
| GET | `/api/users` | `ADMIN` | Список пользователей |
| PATCH | `/api/users/{id}` | `ADMIN` + CSRF | Изменить роль/активность |
| GET | `/api/roles` | `ADMIN` | Справочник ролей |
| GET | `/api/regions` | Вошедший пользователь | Доступные активные регионы; менеджеру — только текущие назначения |
| GET | `/api/products` | Вошедший пользователь | Чтение каталога |

Окончательный OpenAPI-контракт развёрнутого backend: `/v3/api-docs`; визуальное представление: `/swagger-ui/index.html`.

### Регистрация

```json
{
  "login": "manager01",
  "email": "manager@example.org",
  "fullName": "Анна Иванова",
  "password": "your-own-strong-password"
}
```

Успешная регистрация возвращает 201, вход и профиль — 200. Логин содержит 3–60 латинских букв, цифр, точек, дефисов или подчёркиваний; пароль — 8–72 символа и не более 72 байт UTF-8. Логин и email нормализуются к нижнему регистру.

Роль и назначения не принимаются из публичной формы. Нельзя передать `role: "ADMIN"`, чтобы получить повышенные права. Все ограничения длины и формата проверяет backend; frontend показывает соответствующие ошибки.

### Вход

```json
{
  "login": "manager01",
  "password": "your-own-strong-password"
}
```

Вход по логину — отдельное поле, он не подменяется email. Регистрация, вход и `/me` возвращают профиль без хеша пароля:

```json
{
  "id": 12,
  "login": "manager01",
  "email": "manager@example.org",
  "fullName": "Анна Иванова",
  "role": "MANAGER",
  "roleName": "Менеджер по продажам",
  "active": true
}
```

### Изменение пользователя администратором

```json
{
  "role": "ANALYST",
  "active": true
}
```

Можно передать одно из полей или оба; пустое изменение возвращает 400. Администратор не может отключить себя или снять собственную роль администратора. Изменение роли и блокировка учитываются в существующих сессиях при следующем защищённом запросе.

## Google OpenID Connect

Начало потока: `GET /oauth2/authorization/google` в браузере, callback: `/login/oauth2/code/google`. Это OAuth redirect flow, а не JSON-endpoint для передачи email или frontend-токена. После успешного входа backend направляет браузер на настроенный `FRONTEND_URL`; при ошибке — на страницу входа с признаком ошибки.

Если Google не настроен, `/api/auth/providers` сообщает `false`; парольный вход продолжает работать. Для создания Google-only аккаунта нужен подтверждённый email. Существующая локальная запись с таким же email не связывается автоматически.

## Ошибки

Общий формат:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Проверьте введённые данные",
  "fieldErrors": {
    "email": "Укажите корректный email"
  }
}
```

| HTTP | Значение |
| --- | --- |
| 400 | Неверный формат или обязательные поля |
| 401 | Неверные учётные данные или отсутствует действующая сессия |
| 403 | Недостаточно прав (`FORBIDDEN`) либо отсутствует/неверен CSRF-токен (`CSRF_INVALID`) |
| 404 | Запрашиваемый ресурс не существует |
| 409 | Уникальность или конфликт состояния |

Точные коды ошибок зависят от операции; клиент должен ориентироваться на HTTP-статус и поле `code`, а пользователю показывать `message`.
